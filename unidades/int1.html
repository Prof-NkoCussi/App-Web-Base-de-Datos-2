18. Caso práctico: diseñamos una base de datos desde cero

Del problema real a las tablas

En este caso práctico vamos a diseñar una base de datos para una tienda. Queremos guardar clientes, productos y ventas de forma ordenada, sin repetir información.

Paso 1: identificar la información

  • Clientes

    • nombre
    • email
    • ciudad

  • Productos

    • nombre
    • precio
    • stock

  • Ventas

    • fecha
    • cliente
    • total

  • Detalle de venta

    • producto
    • cantidad
    • subtotal

Paso 3: relaciones

Idea clave: Diseñar una base de datos consiste en identificar entidades, separar la información en tablas y conectarlas mediante claves.

Los cuatro pasos y dónde repasar cada uno

TP2 y TP3

1. Modelar

En el problema se marcan tres tipos de palabras:

  • Sustantivos: candidatos a entidades (socio, libro).
  • Verbos: candidatos a relaciones (un socio pide prestado un libro).
  • Características de cada cosa: atributos.

Con eso se dibuja el DER, con la cardinalidad de cada relación (1:1, 1:N o N:M). En UML, cada entidad es una clase, con atributos y métodos.

Para repasar

  • TP2, lámina 4: el DER.
  • TP2, lámina 5: la cardinalidad.
  • TP3, lámina 7: el diagrama de clases.

TP2

2. Pasar a tablas

  • Cada entidad, una tabla; cada atributo, una columna, y el identificador, la clave primaria.
  • En una relación 1:N, la clave foránea va en la tabla del lado N.
  • En una relación N:M, se agrega una tabla intermedia, con una clave foránea hacia cada tabla.

Ejemplo: una editorial publica muchos libros (1:N): id_editorial va en LIBROS. Un socio pide prestados muchos libros y a un libro lo piden muchos socios (N:M): la tabla intermedia es PRESTAMOS, con id_socio e id_libro.

Para repasar

  • TP2, lámina 6: del DER a las tablas.

TP4

3. Claves y restricciones

  • Clave primaria: identifica cada fila; no se repite ni queda vacía.
  • Candidatas y alternativas: las candidatas podrían ser la primaria; las que no se eligen son alternativas, con UNIQUE y NOT NULL.
  • Clave foránea: la clave primaria de otra tabla.
  • Restricciones: NOT NULL, UNIQUE, DEFAULT y CHECK (una condición, como precio > 0).

Una clave primaria de dos campos va al final: PRIMARY KEY (id_alumno, id_curso).

Para repasar

  • TP4, lámina 11: las restricciones.
  • TP4, lámina 12: la integridad referencial.
  • TP4, lámina 13: las claves.

TP5

4. Normalizar

  • Dependencias funcionales: qué campo determina a cuál (A → B).
  • Formas normales: 1FN, un valor por celda; 2FN, todo depende de la clave completa; 3FN, nada depende de un campo que no es clave.
  • Datos que se pueden calcular: guardarlos es repetir información; si cambia un dato del que salen, hay que recalcularlos.

Ejemplo: edad se calcula con fecha_nacimiento y, además, cambia todos los años.

Para repasar

  • TP5, láminas 14 y 15: la redundancia.
  • TP5, lámina 16: las dependencias.
  • TP5, lámina 17: las formas normales.
  • TP5, “Para profundizar”: repetir a propósito.
